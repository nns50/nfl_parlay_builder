### Codec — the `-0` / `+0` leg_id fork is FIXED (sighting 2, promotion condition met)

Run 23 caught this by hand and pre-registered it: *"registering as sighting 1 of the
zero-rung/leg_id-formatting class; if it recurs, promote to a selftest assertion."*
**It recurred this run** — GB@MIN is quoted pick'em, and `format_leg_id(..., 0.0)` renders
`spreads:MIN:+0:` while the ledger has carried `spreads:MIN:-0:` since run 13. Same rung,
two strings; a rung already in the ledger reads brand new.

The cause is in the codec itself, not in a caller: `f"{point:+g}"` formats `0.0` as `+0` and
`-0.0` as `-0`, so **which of the two you get depends on a signed zero nobody is tracking**.
Two changes:

1. **`tools/legs.py` — `format_leg_id` normalises the pick'em spread to the single canonical
   `-0`**, which is what the ledger already carries (`BUF_HOU:spreads:HOU:-0:` and
   `GB_MIN:spreads:MIN:-0:`, 2 rows each). Non-spread markets are unaffected and stay unsigned.
2. **`tools/selftest.sh` §16 — an assertion pins it**: all three of `0.0`, `-0.0` and `0`
   must produce one leg_id, that leg_id must be `-0`, it must parse back to `point == 0`, and
   a totals 0 must still render unsigned. **Verified to FAIL on injected drift** — reverting
   the codec line turns the check red with `pick'em leg_id forked on signed zero`, and
   restoring it returns **97/97**.

This is the run-13 lesson applied to code rather than prose: a correction that lives only in
a build file regresses. Run 23 wrote the correct diagnosis into `builds/`, and the same fork
was waiting in the codec 22 hours later.
